# System files

Root-owned files from `/etc` and `/usr/local/bin` that this laptop depends on.
The install script does not copy them: they control how the machine boots, so
put them in place by hand and check each one first. The login screen's two
files are the exception; see [The login screen](#the-login-screen). The folder layout mirrors
the paths on the system.

| File | What it does |
| --- | --- |
| `etc/modprobe.d/thinkpad_acpi.conf` | Lets `bin/set-fan` control the ThinkPad fan |
| `etc/dracut.conf.d/cmdline.conf` | Kernel command line for the boot images: encrypted root unlocked by the TPM, hibernation, fan control, and a quiet boot. The GPU (Meteor Lake) uses `i915`, the driver Intel supports for it; `xe` runs it only when forced, which taints the kernel |
| `etc/dracut.conf.d/tpm2.conf` | Puts the TPM's libraries in the boot images. See [Unlocking with the TPM](#unlocking-with-the-tpm) |
| `etc/dracut.conf.d/drivers.conf`, `flags.conf` | Extra drivers, zstd compression and host-only images |
| `etc/dracut.conf.d/secureboot.conf` | Signs the images with the sbctl keys |
| `usr/local/bin/boot-image` | Builds one signed boot image per installed kernel, and lists them with their firmware entries. See [The boot images](#the-boot-images) |
| `etc/pacman.d/hooks/90-dracut-install.hook`, `60-dracut-remove.hook` | Run `boot-image`: build a kernel's image when its package is installed or updated, and remove the image when the package is removed. They take the place of dracut's own hooks of the same name |
| `etc/systemd/system/plymouth-quit.service.d/retain-splash.conf` | Keeps the boot splash on screen until the login screen takes over |
| `etc/systemd/system/systemd-pcrlogin@954.service.d/skip-greeter.conf` | Stops a TPM measurement of the greeter user from holding the login screen back by about 1.7 seconds. `954` is the greeter's user id on this machine; check it with `id -u greeter` and rename the folder if it differs |
| `etc/greetd/config.toml` | The login screen: runs the script below on the first console |
| `usr/local/bin/nocturne-greeter.sh` | Generated by `nocturne/build`. Starts the Nocturne login screen (`greeter/`, copied to `/etc/greetd/nocturne/`) inside labwc, and falls back to tuigreet if that cannot start. Needs `greetd`, `labwc`, `wlr-randr`, `quickshell` and `greetd-tuigreet` |
| `etc/pam.d/polkit-1` | The fingerprint for the polkit password window. See [Fingerprint](#fingerprint) |
| `etc/pam.d/greetd` | The login screen's PAM file: the package's, plus the GNOME keyring, which the password unlocks. No fingerprint |
| `usr/local/bin/lid-closed` | Tells the polkit PAM file that the lid is shut, so it skips the sensor |
| `etc/systemd/sleep.conf.d/hibernate.conf` | Sleep, then hibernate after two hours on battery. See [Sleep](#sleep) |
| `etc/systemd/logind.conf.d/lid.conf` | Closing the lid does the same |
| `etc/tlp.d/10-power.conf` | What TLP's three power profiles do, and the battery's charge limits. See [Power and battery](#power-and-battery) |
| `etc/systemd/system/libvirt-docker-forwarding.service` | Lets virtual machines reach the network while Docker runs. See [Virtual machines beside Docker](#virtual-machines-beside-docker) |
| `etc/NetworkManager/conf.d/wifi-powersave.conf` | Turns Wi-Fi power saving off for every connection |
| `etc/X11/xorg.conf.d/90-touchpad.conf` | Tap to click under Xorg, for the i3 session. Hyprland has its own setting |

[REINSTALL.md](../REINSTALL.md) installs Arch from the ISO up to these files,
including the swap file that hibernation uses.

## Placeholders in cmdline.conf

`cmdline.conf` holds three values that identify this machine's disks, so the
repo keeps placeholders. Fill them in when installing:

| Placeholder | How to find it |
| --- | --- |
| `<LUKS_UUID>` | `sudo blkid -s UUID -o value /dev/<encrypted partition>` |
| `<SWAP_UUID>` | `findmnt -no UUID -T /swapfile` |
| `<SWAP_OFFSET>` | On ext4, `sudo filefrag -v /swapfile`, first physical offset. On btrfs, `sudo btrfs inspect-internal map-swapfile -r /swapfile`; `filefrag` is wrong there. `genswap` prints both swap values on either |

## Installing

```sh
sudo install -Dm644 etc/modprobe.d/thinkpad_acpi.conf /etc/modprobe.d/thinkpad_acpi.conf
sudo install -Dm644 -t /etc/dracut.conf.d etc/dracut.conf.d/*.conf
sudo install -Dm644 -t /etc/pacman.d/hooks etc/pacman.d/hooks/*.hook
sudo install -Dm755 -t /usr/local/bin usr/local/bin/boot-image
sudo install -Dm644 -t /etc/systemd/system/plymouth-quit.service.d etc/systemd/system/plymouth-quit.service.d/retain-splash.conf
sudo install -Dm644 -t /etc/systemd/system/systemd-pcrlogin@954.service.d etc/systemd/system/systemd-pcrlogin@954.service.d/skip-greeter.conf
sudoedit /etc/dracut.conf.d/cmdline.conf   # replace the three placeholders
```

The fingerprint, sleep, power and network files are installed the same way;
their sections below have the commands.

## The boot images

There is no boot loader. Each installed kernel has one signed file on the EFI
partition, named after its package, and the firmware starts that file directly
from a boot entry of its own:

| Kernel | Image | Boot entry | For |
| --- | --- | --- | --- |
| `linux` | `EFI/Linux/arch-linux.efi` | `Arch Linux (linux)` | Every day |
| `linux-lts` | `EFI/Linux/arch-linux-lts.efi` | `Arch Linux (linux-lts)` | The way back when the first does not start |

There are two because one image is one way to boot. With a single kernel, an
update that breaks the screen, the disk or hibernation leaves only the Arch
ISO. `linux-lts` is an older, long-term series, so a fault that is new in
`linux` is rarely in it. `linux-zen` would not do as the second kernel: it
follows the same releases as `linux`.

`boot-image` builds the images. For each kernel, dracut packs the kernel, the
initramfs and the command line from `etc/dracut.conf.d` into one file and
signs it. The new file is written beside the old one and takes its place only
once it is whole and signed, so a failed build leaves the image that last
worked. The pacman hooks build a kernel's image when its package is installed
or updated, and remove the image when the package is removed.

```sh
boot-image                    # each kernel, its image and its boot entry
sudo boot-image build         # build every image again
sudo boot-image build linux   # or only one
```

Run `boot-image` now and then, and after a firmware update, which can drop
boot entries. It says `fix` for a kernel with no image, an image that still
holds an older kernel, a missing signature or a missing boot entry.

**Choosing at boot.** The firmware tries the entries in its boot order and
goes on to the next when an image is missing or its signature is wrong. A
kernel that starts and then hangs is not such a case: press F12 at the Lenovo
logo and pick `Arch Linux (linux-lts)`. Both images are signed with the same
key, and that is what the TPM checks, so the disk unlocks by itself under
either; `tpm-reenroll status` says whether it did. A session hibernated
under one kernel cannot be resumed by the other. It is lost, as after a power
cut. So after hibernating under the second kernel, pick it again with F12 at
power on.

**After changing a file in `etc/dracut.conf.d`**, the images only pick it up
when rebuilt. Rebuild one, restart into it, and rebuild the other only when
that worked. A mistake in the command line then costs one image, not both:

```sh
sudo boot-image build linux
# restart and check, then:
sudo boot-image build linux-lts
```

**Adding a kernel.** Install its package, and the hook builds its image. Then
give it a boot entry. `boot-image` prints the command for any kernel that has
none:

```sh
sudo efibootmgr --create-only --disk /dev/nvme0n1 --part 1 --label "Arch Linux (linux-lts)" --loader '\EFI\Linux\arch-linux-lts.efi'
efibootmgr                                    # the new entry's number, and the order now
sudo efibootmgr --bootorder XXXX,YYYY,ZZZZ    # linux, linux-lts, Windows, then the rest as listed
sudo efibootmgr --bootnext YYYY               # start the new one once, at the next restart
```

`XXXX`, `YYYY` and `ZZZZ` stand for entry numbers such as `0001`; put in the
real ones that `efibootmgr` lists. `--create-only` keeps the new entry out of
the boot order, so an image that was never tried does not become the default
by itself. `--bootorder` replaces the whole order: list every number that was
in it. After the restart, `boot-image` marks the entry the machine started
from.

**Changing the everyday kernel**, for example to `linux-zen`: install it, add
its entry as above, and start it once with `--bootnext`. When it works, put
its number first in the boot order; `linux-lts` stays second. Removing `linux`
afterwards removes its image. Its entry goes with `sudo efibootmgr --bootnum
XXXX --delete-bootnum`.

Keep `compress="zstd"` in `flags.conf`. At boot, systemd-stub adds small
archives after the initramfs, and the kernel's lz4 decoder cannot tell where
the lz4 data ends. With lz4 the kernel logs `Initramfs unpacking failed:
Decoding failed` on every boot. The machine still starts, but the added
archives are lost.

## Unlocking with the TPM

The disk unlocks by itself at boot, as BitLocker does by default: the TPM
holds a key for it and releases that key only when the machine started
through this Secure Boot setup (PCR 7, which records the Secure Boot state
and the keys that checked each step). A USB stick, Secure Boot turned off or
changed keys all make the TPM refuse, and the disk password is asked for
instead; it always stays as the fallback. The login screen is then the one
door, so the password there, and the firmware password, matter more.

Three parameters at the end of `cmdline.conf` go with it:

| Parameter | What it does |
| --- | --- |
| `rd.luks.options=tpm2-device=auto` | Tries the TPM before asking for the password |
| `rd.shell=0` | No shell in the boot image if something fails. The disk is already unlocked by then, so a shell would be a way in |
| `rd.emergency=reboot` | Restarts instead |

Each boot image is signed and carries its own command line, so none of this
can be changed at the boot menu. A firmware (BIOS) password keeps anyone from
turning Secure Boot off, which would only make the TPM refuse, but it closes
that door earlier.

It needs `tpm2-tools` (in `packages/pacman.txt`): without it dracut refuses
its TPM module and stops before writing the image, so the old image boots and
asks for the password. To set it up, add the three parameters to
`/etc/dracut.conf.d/cmdline.conf` (the real one, with the disk identifiers),
then:

```sh
sudo install -Dm644 etc/dracut.conf.d/tpm2.conf /etc/dracut.conf.d/tpm2.conf
sudo boot-image build linux
```

Restart (it still asks for the password this time), and only then enroll:

```sh
sudo systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/<encrypted partition>   # asks for the disk password
```

The order matters. Once a boot image has TPM support, systemd marks the
start of the operating system in PCR 7 (`os-separator` in the journal),
before the disk unlocks. Enrolling from a boot without that mark ties the key
to a value no later boot reproduces, and the journal says "TPM policy does
not match current system state".

Restart again: no password prompt means it worked. `journalctl -b | grep -i
cryptsetup` shows the unlock. Then build the second kernel's image as well
(`sudo boot-image build linux-lts`). Until it carries the TPM support too,
that kernel asks for the password.

**When the TPM refuses.** A firmware update, a Secure Boot key change or a
revocation list update (fwupd installs those) changes PCR 7. The boot then
asks for the disk password once. Type it, then run `tpm-reenroll`
(`bin/tpm-reenroll`). It finds the encrypted disk from the boot command line
and enrolls the TPM again for the current state; `tpm-reenroll status` says
whether the TPM unlocked this boot and lists the disk's key slots.

**If the boot breaks.** With `rd.shell=0` there is no rescue shell. Try the
other kernel first: F12 at the Lenovo logo (see [The boot
images](#the-boot-images)). If neither starts, turn Secure Boot off in the
firmware, start the Arch ISO, unlock the disk with its password, and fix it
from there; with Secure Boot off the TPM will not unlock anything, which is
the point.

**To go back** to typing the password: `sudo systemd-cryptenroll
--wipe-slot=tpm2 /dev/<encrypted partition>`. The three parameters can stay;
without a TPM key they change nothing.

## A quiet boot

The boot should show Plymouth and nothing else: no text before it, and none
between the disk password and the login screen. Two things do that.

Three parameters at the end of `cmdline.conf`:

| Parameter | What it does |
| --- | --- |
| `loglevel=3` | Hides kernel error lines. `quiet` alone still prints them |
| `systemd.show_status=error` | systemd prints failures only, never the `[ OK ]` lines |
| `vt.global_cursor_default=0` | Hides the blinking text cursor |

Two parameters to leave out:

- `plymouth.nolog`. Plymouth tells systemd to print its status lines whatever
  `systemd.show_status` says, and normally catches them itself and writes
  them to `/var/log/boot.log`. With `plymouth.nolog` it does not catch them,
  so they land on the screen for a moment before the splash draws.
- `plymouth.use-simpledrm`. It makes Plymouth draw the password prompt on the
  firmware display about three seconds sooner. But the GPU's driver then
  takes the display over, and the screen goes black until it is ready and
  Plymouth draws again.

And `retain-splash.conf`, which makes Plymouth leave its picture on screen
when it quits. Without it the text console shows for about two seconds, until
greetd clears the screen for the login screen.

The hidden messages are all still in `journalctl -b`. If the login screen
cannot start at all, the first console keeps showing the frozen splash;
`Ctrl + Alt + F2` opens a plain console.

## The login screen

The login screen is separate and does not touch the boot images. The repo's
`install` sets it up on a new machine, and enables greetd when no other login
manager is enabled. One command installs or updates it:

```sh
nocturne greeter preview   # look at it in a window first
nocturne greeter install   # asks for your password
```

`install` copies the screen to `/etc/greetd/nocturne/`, because the greeter's
user cannot read a home folder, puts the script in `/usr/local/bin`, and
points greetd at it. The desktop's cursor goes along: the theme named in
`hypr/lua/env.lua` is copied into `/etc/greetd/nocturne/icons/` if it lives in
your home folder. The config it replaces is kept as
`/etc/greetd/config.toml.before-nocturne`.

greetd reads its config only when it starts, so the first install shows after
you restart the computer; logging out is not enough. (`sudo systemctl restart
greetd` also works, but it ends your session on the spot.) Later updates show
at the next login.

The copies do not follow the repo by themselves. After changing the accent or
the wallpaper, run `nocturne greeter install` again; `nocturne reload` and
`nocturne doctor` say when they are out of date.

**Sessions.** Every login starts Hyprland unless you pick another session in
the bottom-left corner first (click it, or Tab to it and press Enter). GNOME
appears when it is installed, and i3 when it and `xorg-xinit` are; a session
other than Hyprland shows in gold, and the next boot starts at Hyprland
again. `greeter/session.sh` starts each one: GNOME on Wayland, and i3 through
`startx` on the login's console. GDM can stay installed, disabled, as a way
back to GNOME's own login screen.

If the screen cannot start, the script falls back to tuigreet, the text
login, so you can still get in. It starts Hyprland too; F3 there lists the
other sessions. `Ctrl + Alt + F2` opens a plain console as a
last resort. To go back for good:

```sh
sudo cp /etc/greetd/config.toml.before-nocturne /etc/greetd/config.toml
```

## Fingerprint

Enrol a finger first (`fprintd-enroll`). The lock screen then needs nothing
more: hyprlock talks to the sensor itself, alongside the password. For the
polkit password window, the PAM file here puts the fingerprint first:

- **polkit** waits 10 seconds for a finger, then asks for the password.
- **With the lid closed**, as when docked, it skips the sensor and asks for
  the password straight away (`lid-closed`).

The login screen has no fingerprint. The sensor would listen first, and a
password typed meanwhile would wait for it to give up: about 10 seconds
after the screen showed. It is also a password that unlocks the GNOME
keyring, which a fingerprint cannot do.

sudo keeps asking for the password straight away. PAM runs one module after
another, so a fingerprint first would hold every sudo back until the sensor
gives up.

The disk password at boot stays a password.

```sh
sudo install -Dm755 usr/local/bin/lid-closed /usr/local/bin/lid-closed
sudo cp /etc/pam.d/greetd /etc/pam.d/greetd.before-nocturne
sudo install -Dm644 -t /etc/pam.d etc/pam.d/polkit-1 etc/pam.d/greetd
```

Then try `pkexec true`. The login screen's file takes effect at the next
login. To go back, copy `greetd.before-nocturne` back and delete `/etc/pam.d/polkit-1`;
polkit then uses `/usr/lib/pam.d/polkit-1` again. When the greetd package
changes its own file, pacman leaves the new one beside it as `.pacnew`.

## Sleep

Sleeping from the power menu, after 30 idle minutes, or by closing the lid
runs `systemctl suspend-then-hibernate`. On battery, the laptop hibernates
after two hours asleep (or sooner, if the battery runs low), so it never
drains flat; on the charger it stays asleep. With an external display
connected, closing the lid still does nothing. Hibernation must already work:
the swap file and the `resume=` values in `cmdline.conf`, as REINSTALL.md
step 6 sets them up.

```sh
sudo install -Dm644 -t /etc/systemd/sleep.conf.d etc/systemd/sleep.conf.d/hibernate.conf
sudo install -Dm644 -t /etc/systemd/logind.conf.d etc/systemd/logind.conf.d/lid.conf
sudo systemctl kill -s HUP systemd-logind   # reads the lid setting again; your session stays
```

## Power and battery

TLP has three profiles. It picks **performance** on the charger and
**balanced** on battery, and the launcher's power menu and the control
centre's performance switch pick one by hand through `tlpctl`, which the
`tlp-pd` service answers. `install` enables TLP and that service.

`etc/tlp.d/10-power.conf` says what the profiles do on this laptop:

- **Performance** lets the processor run as fast as it can.
- **Balanced** is set for battery life, the same as **power-saver**, because
  it is the profile the laptop is in whenever it is unplugged.
- **Wi-Fi power saving** is off in every profile. TLP's default turns it on
  in balanced and power-saver, which would undo `wifi-powersave.conf` (see
  [Wi-Fi and the touchpad](#wi-fi-and-the-touchpad)) each time the laptop is
  unplugged.
- **The battery** starts charging only below 80% and stops at 90%. A battery
  that is not kept full lasts more years. To fill it once before a trip:
  `sudo tlp fullcharge`.

```sh
sudo install -Dm644 -t /etc/tlp.d etc/tlp.d/10-power.conf
sudo tlp start          # applies it now
tlp-stat -c             # every setting, and the file it came from
```

TLP reads `/etc/tlp.conf` after the files in `/etc/tlp.d`, and the last value
wins. Keep these settings out of `/etc/tlp.conf`, or the copy there quietly
overrides this one. The names here end in `_PRF`, `_BAL` and `_SAV`; TLP 1.11
renamed the older `_AC` and `_BAT`, and `tlp-stat -c` marks any that are left.

## Virtual machines beside Docker

Docker drops forwarded traffic it does not know about, and that includes the
traffic of libvirt's virtual machines: with Docker running, a machine on the
default network (`virbr0`, `192.168.122.0/24`) cannot reach the internet.
`libvirt-docker-forwarding.service` adds two rules to the chain Docker keeps
for this, `DOCKER-USER`, each time Docker starts: traffic from the virtual
machines may pass, and so may the replies to it.

```sh
sudo install -Dm644 -t /etc/systemd/system etc/systemd/system/libvirt-docker-forwarding.service
sudo systemctl daemon-reload
sudo systemctl enable --now libvirt-docker-forwarding.service
sudo iptables -S DOCKER-USER      # shows the two virbr0 rules
```

The rules name libvirt's default network. A network with another bridge or
address range needs its own lines in the service.

## Wi-Fi and the touchpad

Two small files, each one setting:

```sh
sudo install -Dm644 -t /etc/NetworkManager/conf.d etc/NetworkManager/conf.d/wifi-powersave.conf
sudo systemctl reload NetworkManager      # applies at the next connection
sudo install -Dm644 -t /etc/X11/xorg.conf.d etc/X11/xorg.conf.d/90-touchpad.conf
```

`wifi-powersave.conf` tells NetworkManager to turn the Wi-Fi card's power
saving off on every connection (`2` means off). `iw dev <interface> get
power_save` shows the current state. TLP has a setting for the same thing,
and `10-power.conf` keeps it off as well, so the two agree.
`90-touchpad.conf` turns on tap to click
for the i3 session, which runs on Xorg; it shows at the next i3 login.
